# 多層レイヤー構造（A/B/C/D層）— この repo での実装

> 導入: 2026/07/13。「AI を1人のチャット相手」ではなく「層で動くシステム」として運用するための設計書。
> **翔さんが新しく覚えることはゼロ。** 発注は今まで通り日本語1本。層の切り替えは全部 Claude の仕事。

## 4層の対応表（設計 → この repo での実体）

| 層 | 役割 | この repo での実体 |
|----|------|-------------------|
| **A層** 文脈の共通化 | キャラクター・行動規範・ドメイン辞書を常時ロード | `CLAUDE.md` + `.claude/hooks/session-start.sh` + `context/me.md` ほか context 一式 |
| **B層** 動的な役割分業 | 司令塔がタスクを分解し、専門サブエージェントを並列駆動 | メインの Claude（司令塔）+ `.claude/agents/` の3班（下記） |
| **C層** 知識の還流 | 成果物・暗黙知を日次/週次で仕分けし、A層へ昇格 | R-daily（朝刊・提案）+ R-weekly（learnings.md への振り返り + **昇格チェック**） |
| **D層** 直前検問 | ハルシネーション遮断・暴走防止のガードレール | クリティカル7 + `settings.json` の許可/確認リスト + 各班のツール制限 + **検算班** |

## B層: サブエージェント3班（切り方は「部門」でなく「機能」）

部門で5体に割らない理由: 同じ禁則を5回書くことになり、休眠中の領域（副業・家計）に過剰投資になる。
機能で割れば、ガードレールを各1箇所に書くだけで全部門に効く。部門の知識（customers.md 等）は班に「持たせる文脈」として差し込む。

| 班 | ファイル | 担当 | 持ち物（ツール） | 持たせないもの＝ガードレール |
|----|---------|------|-----------------|---------------------------|
| **調査班** | `.claude/agents/chosa-han.md` | Web 調査・市況・競合・ニュース | Web 検索・閲覧、repo 読み書き | **customers.md・顧客文脈**（Web への漏洩を構造的に遮断）。送信系なし |
| **起案班** | `.claude/agents/kian-han.md` | 文書・メール・SNS の下書き | repo 読み書き、Gmail **下書き作成まで** | **送信ツール・Web 検索**（下書きが勝手に外に出ない） |
| **検算班** | `.claude/agents/kensan-han.md` | 数字入り成果物の直前検問（D層の実体） | 読み取り + 計算のみ | **書き込み・送信すべて**（検査役は手を動かさない） |

### 班の連携パターン（例: 「◯◯社向けの見積つくって」）

```
翔さん「◯◯社にSS400の見積、100枚で」
  → 司令塔がティア判定（中）
  → 起案班: customers.md + 過去見積を参照して見積ドラフト作成
  → 検算班: 単価の根拠・原価混入・納期を検問 →「⚠ 要修正」or「✅ 通過」
  → 司令塔が翔さんに提示（人間確認必須スタンプ付き）
  → 翔さんが単価を最終判断 → 送信は人間
```

## ティア宣言（司令塔の初期判定）

| ティア | 目安 | 動き方 |
|--------|------|--------|
| **軽** | 質問・1成果物の定型 | 即答・即実行。宣言不要 |
| **中** | task_templates.md に該当・単一部門 | テンプレの出力先/確認ルール適用 → 実行 → 事後報告 |
| **重** | 部門横断・成果物3つ以上・数時間規模 | 実行計画を1画面提示 → 翔さんの「OK」→ 班を並列駆動 |

- クリティカル7（`ai_operations_flow.md`）はティアに関係なく常に優先
- 「寝る前セット。市況と訪問準備とSNS案」のようなまとめ発注は自動的に**重**扱い → 計画1画面 → OK で並列

## C層: 閉ループ（使うほど A層が賢くなる仕組み)

```
日々の発注 → 成果物 + ops_log（Claude が記録）
    ↓ 毎週日曜 21:00
R-weekly が集計 → learnings.md に振り返り
    ↓ 昇格チェック
3回以上繰り返された指示・訂正 → CLAUDE.md / task_templates / me.md への昇格案（最大1つ）
    ↓ 翔さんが「OK」
A層に反映 → 以後すべてのセッション・全端末・どのモデルでも同じ解釈で動く
```

昇格は**自動では書き換えない**（R-weekly は提案まで、反映は OK 後）。
このループがあるから、モデルが Fable でも Opus でも Sonnet でも「repo に蓄積したルール」が効く。

## D層: ガードレール一覧（どこで何が止まるか）

1. **ツール制限**（構造）— 各班は必要最小限のツールしか持たない。調査班は顧客情報に触れず、起案班は送信できない
2. **settings.json**（構造）— 削除・強制 push・Slack 送信などは翔さんの承認が必須（ask リスト）
3. **検算班**（検問）— 金額・数量・納期を含む成果物は提示前に必ず通す。出典なしの数字を全件列挙（ハルシネーション遮断）
4. **クリティカル7**（規範）— 金額確約・顧客送信・採用・繊細対応・税務・大型支出・重要顧客対応は必ず人間
5. **増築禁止**（暴走防止）— 新しい仕組みは既存が2週間回ってから。複雑化は Claude が自分から止める

## 検収方法（次のセッションで試す）

サブエージェントは**セッション開始時に読み込まれる**ため、この設計の動作確認は導入後の新しいセッションで行う。

1. 「直近1週間の鋼材市況を調べて」→ **調査班**が起動し、出典 URL 付きで返ってくるか
2. 「◯◯社へのお礼メール下書いて」→ **起案班**が起動し、Gmail 下書き or ファイルで止まるか（送信されないか）
3. 数字入りの成果物に**検算班**の検問結果と「人間確認必須」スタンプが付くか
4. うまく動かない班があれば、このファイルと `.claude/agents/` の該当ファイルを直す（翔さんは「◯◯がおかしい」と言うだけでいい）
